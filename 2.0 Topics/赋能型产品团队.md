# 赋能型产品团队

Empowered product team 不是“团队可以自己选想做的功能”，而是组织把一个重要 problem/outcome、必要的战略上下文和解决问题的权力交给跨职能团队，并要求它对实际结果负责。

## Feature team 与 empowered team 的根本差异

| 维度 | Feature team | Empowered product team |
|---|---|---|
| 输入 | Stakeholder 排序后的 feature/project | 客户或公司的 problem、目标 outcome |
| 决策 | 高层先决定 solution | 团队通过 discovery 找 solution |
| PM 角色 | 收集需求、写文档、协调进度 | 降低 value 与 viability 风险 |
| Designer | 美化和出稿 | 共同定义 experience，降低 usability 风险 |
| Engineer | 实现需求 | 利用技术知识参与 solution discovery |
| 成功标准 | 是否按时上线、完成多少 output | 是否解决 problem、改变 outcome |
| 学习方式 | 发布后看结果 | Prototype、用户测试、数据与技术探索持续学习 |

外观上的 squad、sprint、roadmap、daily stand-up 并不能证明团队被赋能。Marty Cagan 认为，如果团队接到的是固定 solution，它即使使用 Agile，也仍然是 feature team。

## 为什么决策应该下放

一线 engineer 每天接触 enabling technology，产品团队每周接触用户和客户。他们掌握的信息比季度 roadmap 会议更接近问题本身。下放决策并不是浪漫化自主权，而是把 solution decision 放到信息最充分的位置。

但授权有三个前提：

1. **明确的 problem/outcome**：团队知道要改变什么，而不是只听到“做点创新”。
2. **Strategic context**：团队理解 product vision、strategy、其他团队工作和业务约束。
3. **足够能力**：PM、designer 和 engineer 能共同处理 value、usability、feasibility、viability 风险。

缺少其中任意一个，所谓 empowerment 都可能变成失控、局部优化或重新回到高层指定 feature。

## PM 必须带入团队的四类知识

Marty 把 PM 的贡献压缩成四个知识领域：

1. **Users and customers**：不能只依赖 researcher 或 sales 的二手转述。
2. **Data**：理解产品如何被使用、行为如何变化、销售与用户分析说明什么。
3. **Business**：理解 marketing、sales、monetization、privacy、security、compliance 等约束，并取得 stakeholder 信任。
4. **Market**：理解竞争格局、行业趋势和替代方案。

这些知识不是为了让 PM 独自决定 solution，而是让 designer 和 engineer 的体验与技术判断能够连接真实市场和业务。

## 三条不能被切断的关系

PM 可以把 project management、QA、product marketing 或大量 runtime 工作交给专业角色，但不应失去：

- 对 users/customers 的直接接触；
- 与固定 engineers 日常共同解决问题的关系；
- 对 stakeholders 的直接接触和信任。

某些 Product Ops 或 Product Owner 设计会在这些关系中增加中间层。其原意可能是减轻 PM 工作量，实际却可能拆散形成产品判断所需的信息网络。

## 常见退化路径

```text
公司依靠好产品获得成功
→ 规模扩大，销售、营销和成本控制成为增长手段
→ 产品人才减少，领导层不再理解 discovery
→ 为降低风险，组织只做小型优化和 A/B test
→ Stakeholder 直接规定 feature
→ PM 变成项目管理员
→ 新价值创造停止
```

这里不是说 sales、marketing、finance 或 optimization 不重要，而是组织不能只剩 value capture，失去 [[产品发现（Product Discovery）|value creation]]。

## 实际转型方式

个人贡献者很难直接改变整个公司，但可以申请一个有边界的团队实验：

1. 选择一个季度内可观察结果的重要 problem；
2. 把既定 feature 反推成 success metric；
3. 明确团队的直接客户、工程与 stakeholder access；
4. 补齐 PM 的四类知识和战略上下文；
5. 使用 discovery 技术比较多个 solution；
6. 用 outcome 复盘，而不是展示完成了多少 feature。

这些步骤是判断和试验框架，不是一套必须照抄的流程。真正关键的是把 feature 重新连接到 problem/outcome，并补齐团队的 access、能力和战略上下文。
