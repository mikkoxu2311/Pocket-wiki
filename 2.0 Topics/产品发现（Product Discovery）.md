# 产品发现（Product Discovery）

Product discovery 是团队在大规模交付前后持续降低产品风险、建立用户模型并寻找 winning solution 的过程。它不是“先做几周用户研究，再把 PRD 交给工程”的固定阶段。

## Discovery 在解决什么风险

一个 solution 要同时通过四类检验：

- **Value**：用户是否愿意使用或购买？
- **Usability**：目标用户能否理解并使用？
- **Feasibility**：现有技术、时间和团队能否实现？
- **Viability**：是否符合商业、法律、安全、销售和运营约束？

不同角色承担不同专长，但这些风险相互依赖。一个安全合规但没有价值的产品、一个用户喜欢但无法盈利的产品、一个体验优秀却无法实现的产品，都仍然是失败。

## Problem discovery 与 solution discovery

Marty Cagan 区分两种 discovery：

1. 确认应该解决哪个 problem；
2. 找到用户会选择的 solution。

一个常见错误是，无论 problem 是否已经高度确定，团队都照流程花数周“验证问题”。在创业公司里，founder、客户和团队可能已经十分了解 problem，此时最大的风险是 solution 是否真的优于替代方案。

用户不会因为 problem 描述得正确而购买。他们购买的是在具体约束下比其他选择更好的 solution。因此，problem discovery 的深度应与不确定性匹配，把更多时间留给真正危险的环节。

## Discovery 不是让用户批准方案

User research 不应被简化成“给足够多人看 prototype，大家说喜欢就开发”。它至少承担两项工作：

- **Generative**：扩展团队对用户情境、需求和机会空间的理解；
- **Evaluative**：主动寻找用户不会采用、无法理解或无法完成任务的原因。

Research 的长期产物不是一堆报告，而是团队逐渐形成的用户 mental model。这个模型帮助团队在没有实时访谈时也能提出更好的假设。

## 为什么团队必须直接参与研究

Researcher 单独访谈再交报告，会把关键学习压缩成二手结论。Marty 建议 PM 和 designer 必须在场；Lenny 的 Airbnb 案例还显示 engineer 参与也会显著提高团队理解。

直接参与有三个作用：

1. 团队听见用户的语言、犹豫和情境，而不只看到标签；
2. Designer 和 engineer 能即时联想到新的 solution space；
3. 团队对证据产生共同记忆，减少事后争论“用户到底是不是这个意思”。

## 三种互补工具

### [[机会解决方案树（OST）]]

从 desired outcome 出发，把 opportunity、多个 solution 和 assumption test 连接起来，防止团队从一个访谈直接跳到一个功能。

### [[Jobs to Be Done（JTBD）]]

重建 struggling moment、改变力量、焦虑与现状习惯，帮助团队理解 demand 为什么出现，以及真实竞争者是谁。

### [[可信实验与 A-B Testing]]

当 solution 已经能够上线并量化时，实验帮助判断变化是否造成结果。它适合回答“是否产生影响”，但不能独自解释“为什么用户这样行动”。

## Value creation 与 value capture

Discovery 更偏向创造新的价值，funnel optimization 和小型 A/B test 更偏向捕获现有价值。成熟公司需要两者，但如果组织因害怕破坏核心业务而只做低风险优化，短期指标可能稳定，长期创新能力却会下降。

## 常见失败方式

- 把 discovery 当作发布前的一次验证仪式；
- 对明确 problem 过度研究，却没有时间比较 solution；
- 只问用户喜不喜欢，不主动寻找不采用的原因；
- Researcher 独立拥有客户知识，团队只读结论；
- Stakeholder 先指定 solution，再要求团队“做 discovery”；
- 用 A/B test 代替对客户情境和需求的理解；
- 只测试 desirability，忽略 feasibility、viability 或 usability。
